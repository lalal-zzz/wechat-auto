# 事件详述与跨时间追踪

用于月度、会话汇总、人物、时间线与重建 Skill。语义模板 `analysis-quality-v7`。
与 [分析质量标准](ANALYSIS_QUALITY_STANDARD.md) 和
[存储契约](MEMORY_STORAGE_CONTRACT.md) 一起执行。本文是 Agent 分析规范，
不是已实现的自动事件识别、合并或质量门禁。

## 1. 事件粒度与覆盖

事件是有具体对象、情境、行动或变化的一件事情，不只是关键词或话题标签。
工作、学业、生活、家庭、健康、活动、合作、金钱和关系中的事情都适用。
不能只列“工作变化”“见面”“争执”三个标题，也不固定每月几个事件。

区分三个层次：

- 长期事项：例如某次求职、一个项目、一次长期备考；有共同目标与连续证据。
- 具体事件：例如某公司面试、某次出游安排、某笔款项、某次明确分歧。
- 阶段或回合：提议、准备、协商、行动、变更、反馈、收尾及后来复盘。

长期事项保留具体事件，不能吞掉不同公司的面试、不同承诺或不同争执。
“找工作”反复出现是话题线索；是否属于同一求职过程、不同轮次或纯转述须核验。
相同参与人/关键词不足以合并；同一事件跨私聊、群聊或朋友圈复述不重复计数。
重要程度依据实际影响、持续时间、承诺、争议及用户关注，不能只按消息数量。
短对话也可能确定一项重要决定；有可复用事实的小事也应保留，不只选“大事情”。

## 2. 每个事件要分析到具体过程

详细事件正文保留以下有证据的内容，未知部分明确说明，不强行填满：

| 维度 | 具体问题 |
|---|---|
| 身份与对象 | 是哪一件事、涉及谁/哪个组织或目标？当事人、转述人、执行人分别是谁？ |
| 起因与背景 | 什么触发、此前有什么相关状态？明确原因与 Agent 的解释候选分别是什么？ |
| 各方诉求 | 谁希望什么、顾虑什么、分歧在哪？引用对方不等于作者也赞同。 |
| 过程与阶段 | 实际经历哪些回合、行动、反馈、暂停或反复？哪个信息改变了走向？ |
| 决定与约定 | 谁提出、谁接受、内容/条件/责任人/期限是什么？口头讨论是否达成决定？ |
| 变更与转折 | 原计划怎样、何时改动、谁提出、对方是否接受、旧约定是否取消？ |
| 结果与影响 | 有什么完成、取消、失败或延后证据？影响了哪些后续安排或关系？ |
| 当前状态 | 截至来源覆盖最后可知进展；未知、未完成与明确取消分别标识。 |
| 未解决事项 | 还缺什么信息、谁需跟进、是否有明确期限？不替用户编造新待办。 |
| 回顾与解释 | 后来怎样回忆或重新评价？当时记录与后来解释是否冲突？ |

用“背景→各方表达→行动/协商→关键转折→结果→后续”连贯叙述，配必要阶段表。
重要事件详细还原对话的推进与回应，不用“双方发生分歧，之后缓和”等概括代替。
解释为什么认为已决定/已完成/已修复时必须给对应证据，而非仅列开始和结束日期。
行为、情绪和关系影响在该事件内有依据地分析；不把一次事件直接升格为永久性格。

### 正文格式（按信息量伸缩）

```markdown
### {具体事件标题} [event_id]

范围：{实际日期或已知范围}；截至：{来源覆盖时间}；状态：{有依据的文字状态}
参与人/对象：{稳定身份、具体角色和目标}

背景与诉求：……

| 时间及精度 | 阶段/具体进展 | 各方行动或回应 | 决定/变更 | 依据 |
|---|---|---|---|---|
| … | … | … | … | [claim_id] |

关键转折与分歧：原先……后来……依据……仍有替代解释……
结果与后续影响：……
未完成事项、反证与来源缺口：……
```

每条阶段关联能支持它的 Claim/证据。没有数据的栏目可合并或省略，但保留缺口。
正文引用短 ID，需要解释时再展开原始上下文；不大量复制聊天，不另建每事件报告文件。

## 3. 跨月、跨年及跨来源事件

月度是处理分区，事件按实际过程组织，不在月初重开、月末关闭。

1. 月度开始读取上版开放事项及相关历史事件，建立本月候选事项；按序阅读时
   记录新增进展、旧事回忆、改动、结果和未完回合。
2. 对“之前那个、上次、后来、又、终于”等指代展开上下文，核对参与人、对象、
   目标、约定、日期和明确回指。没有可靠衔接时保留独立候选和可能关联。
3. 确认为同一事件时沿用 event_id，保留此前有效阶段并加入本月变化。月度正文
   写“此前背景、本月进展、结转状态”，跨月汇总还原完整过程，不拼接重复摘要。
4. 同类事情再次发生时创建独立具体事件，在正文说明重复模式候选；检查对象、
   轮次和结果差异。不能把几次争执压成一条跨两年的连续争执。
5. 长间隔只代表缺少可见更新，不能推断一直持续、已经完成或关系自动修复。
   时间线显示最后证据与未知区间，不画成持续发生的实线。
6. 跨私聊/共同群/朋友圈核对稳定身份及具体事件对象，保留直接观察、自述、
   第三人转述和发布/回忆来源。复述可补解释，不能冒充独立证据提高置信度。
7. 汇总检查：先前承诺是否有完成/取消证据？后来的“终于/没去/换了”指哪件事？
   关键变化是否在月度压缩时丢掉？回查原文后再定终点和状态。

“同一事件持续”“事件导致/影响另一事件”“同类事件反复”“同一话题再次讨论”
分别说明。因果必须有当事人说明或充分支持，否则仅写时间关联/解释候选。
人物层提炼此事件中的个人行为和影响，具体过程仍引用会话正文；群级变化不
自动归给所有成员。持续性与变化都要有证据，不制造每月一个转折。

## 4. 时间、状态与冲突

- 分开记录计划日、截止日、实际发生日、记录日、回忆日、发布/观察日。
  一条今天的“去年做过”不能排成今天发生，也不能把今天“明天准备去”当已去。
- 相对日期结合本条时间与上下文，保留到年/月/日/范围的真实精度，不猜缺失日期。
  历史补入消息按实际发生时间放置，同时注明来源何时被补入。
- 完成、取消、暂停、延期、重启、失败、结果未知是不同业务情况；以文字解释
  原因和证据。先核对当前接口允许的 status，不能将自然语言状态直接写成
  不支持的枚举；可以用短事件状态 Claim 承载细分事实。
- 双方说法冲突并列，标明时间、说话人和依据。后来的回忆不能静默替代当时原句。
- 道歉、继续聊天或一个表情不自动证明问题解决；修复要看回应、调整和后续。
  玩笑/角色演绎/转发/梦与真实发生分开，读至回合结束再定事件。

## 5. 存储、增量和接口边界

正式库固定 `data/wechat_memory.sqlite3`；详细正文仍在所属会话及月份 current.md，
完整历史版本由 analysis.submit 维护。未验收事件笔记留固定工作目录，不另建
events.md、逐事件 YAML 或第二套事件数据库。

SQLite 的 events 保存短标题/概要和索引；event_phases 保存简短阶段与日期，
event_people / event_conversations / event_claims 关联角色来源与相关结论。
阶段行动、变化原因、复杂角色和证据解释用短 Claim + 正文承载，不能把完整报告
塞进事件 summary。实际表未提供阶段级证据关系和复杂事件关系图，不能伪造。

当前 events.upsert 的限制：更新会替换当前阶段，旧关联通常累加而非自动移除；
event_versions 只保存事件标量快照，不保存完整历史阶段及关联快照。
所以提交前读 events.get 并合并此前仍有效阶段，不能只提交本月新增阶段。
阶段拆分/合并须保留可追踪的旧 ID、证据和解释；接口未提供完整事务式拆并/
关联解除时保留修复候选，不声称已完成可重建的历史事件图。

补入旧消息、用户纠正或新结果时，回查受影响事件及相关月份、会话、人物和图表；
不机械重跑所有月份。相同证据/内容先比较，避免重复 upsert 创建无意义事件版本。
新消息可能只是复述，要区分“新增证据”和“事件状态改变”。
提交冲突/证据缺失时保留上一成功正文与候选，重载正确版本后再合并。

## 6. 验收

- 每个重要事件不仅有标题，还能解释背景、各方诉求、过程、转折、结果和缺口。
- 独立事情未被主题大桶吞掉；没有固定事件条数导致的遗漏。
- 跨时间事件有可靠衔接、具体阶段和实际日期，月份边界不充当起止日期。
- 开放承诺有后续核对；无结果证据时仍开放/未知，不擅自闭合。
- 回忆/转述/计划没有冒充实际发生；反证、变更和重复事件仍可区分。
- 每个结论/阶段可追溯，完整阶段提交未丢掉旧有效进展；未支持的历史图能力明确标注。
- 图表只呈现已成功分析的内容，展示未读月份、时间缺口和不确定范围。

仅关键词命中、时间点列表或旧概览不通过；回读原始回合后重建受影响范围。


## v7 主体与分片复核

事件中逐项分离 speaker、actor、fact_owner、relation_owner 与被提及/引用第三方；self 或联系人讲述亲友的安排不创建讲述人的任务。关系双方和称谓所属者按 scoped reference 保留，未知身份不合并 Person。跨片边界回查完整回合，跨月产出保留已有阶段；每月由独立 Agent 展开关键原回合核验归属，协调者串行提交。事件详细正文与全部非事件维度共同构成正式 Markdown，用户 HTML 从同一成功版本全量渲染，不能用事件报告代替全面分析。
